# LOST REGALIA — 기술 설계서

> 버전 0.1 · 2026-11-16 · 엔진: Unity 6
> 짝 문서: [GDD 17장](./02_gdd.md#17-기술과-스팀-출시) · [전투 규칙](./06_combat_rules.md) · [곶 생성 규칙](./07_cape_generation.md) · [프로토타입 사양서](./03_prototype_spec.md)
> 코드: `sim/` (시뮬레이션 코어. 이미 컴파일되고 테스트된다)

이 문서의 가장 큰 결정은 **시뮬레이션을 Unity에서 떼어 낸 순수 C# 코드로 둔다**는 것이다. 글로만 정하지 않고 뼈대를 실제로 작성해 컴파일하고 테스트했다. 4장에 그 결과가 있다.

```bash
dotnet run --project sim/Tests~/Tests -c Release
```

## 1. 결정 요약

| 항목 | 결정 | 이유 |
|---|---|---|
| 엔진 | Unity 6, URP | 확정 사항 |
| 구조 | **시뮬레이션(순수 C#)과 화면(Unity)을 나눈다** | 규칙을 Unity 없이 테스트한다. 저장과 되감기가 단순해진다 |
| 시간 | 고정 틱, 초당 30회 | 결과가 프레임 속도에 따라 달라지지 않는다 |
| 난수 | 시뮬레이션 안의 자체 난수 하나 | 같은 시드는 같은 결과. 상태에 그대로 저장된다 |
| 적의 이동 | 길 찾기 없음. 레인 번호와 높이 값 하나 | 등반은 일차원이다. 200기가 틱 하나에 0.01ms도 쓰지 않는다 |
| ECS / DOTS | **쓰지 않는다** | 시뮬레이션 비용이 사실상 0이다. 병목은 그리기이고, 그것은 ECS 없이 푼다 |
| 물리 | 시뮬레이션은 PhysX를 쓰지 않는다 | 결정성. 성벽과 타일은 격자와 구간으로 판정한다 |
| 규칙 데이터 | 저장소의 `data/*.json`이 원본 | 파이썬 도구, C# 시뮬레이션, 문서가 같은 파일을 읽는다 |
| 저장 | 상태 전체의 스냅숏 | 되감기는 스냅숏을 불러오는 것이다 |
| 입력 | Input System | 키보드·마우스와 게임패드, 키 재설정 |
| 카메라 | Cinemachine | 성벽과 곶에서 시점 오프셋이 다르다 |
| 화면 UI | **UI Toolkit** | UI 에셋 팩을 쓰지 않고 직접 만든다. 7.7 참조 |
| 테스트 | Unity 없이 `dotnet`으로 돌린다 | 에디터를 켜지 않고 규칙을 검증한다 |

## 2. 원칙

1. **시뮬레이션은 화면을 모른다.** `sim/`의 코드는 `UnityEngine`을 참조하지 못한다. 어셈블리 정의에서 막아 두었다.
2. **수치를 코드에 적지 않는다.** 체력, 피해, 비용, 강도는 전부 `data/`에 있다. 코드에 있는 수는 틱 속도 같은 엔진 상수뿐이다.
3. **문서의 표와 코드는 같은 값을 낸다.** 문서의 표는 파이썬 도구가 데이터에서 계산해 채운다. 같은 도구가 기대값을 내보내고, C# 테스트가 그것과 대조한다.
4. **같은 시드는 같은 결과.** 시뮬레이션은 자체 난수와 고정 틱만 쓴다. 시각, 프레임 시간, Unity의 난수를 읽지 않는다.
5. **조합은 조립한다.** 기술을 하나씩 코드로 쓰지 않는다. 전달 방식 일곱 가지와 수식어의 조합으로 데이터에서 만든다.

## 3. 구조

```
   data/*.json ──────────►┌──────────────────────┐
   (규칙의 원본)            │   LostRegalia.Sim    │◄──── 입력 (틱마다 한 묶음)
                          │   순수 C#. Unity를 모른다 │            ▲
                          └──────────┬───────────┘            │
                                     │ 상태 (읽기 전용) · 사건     │
                                     ▼                        │
                          ┌──────────────────────┐            │
                          │   LostRegalia.Game   │── 입력 수집 ─┘
                          │   Unity: 그리기, 소리,  │
                          │   카메라, UI, 저장 파일  │
                          └──────────────────────┘
```

### 3.1 어셈블리

| 어셈블리 | 위치 | 하는 일 | 참조 |
|---|---|---|---|
| `LostRegalia.Sim` | `sim/Runtime/` | 규칙, 상태, 틱, 스냅숏 | 없음. `noEngineReferences` |
| `LostRegalia.Game` | `game/Assets/Game/` | 시뮬레이션을 돌리고 그린다. 입력, 카메라, 소리, 효과 | Sim, Unity |
| `LostRegalia.UI` | `game/Assets/UI/` | HUD, 왕좌 메뉴, 각성 트리 화면 | Sim, Game |
| `LostRegalia.Editor` | `game/Assets/Editor/` | 데이터 복사, 생성기와 광부 도구, 디버그 창 | 전부 |

### 3.2 저장소

```
data/        규칙의 원본 (JSON). 파이썬 도구와 C#이 함께 읽는다
sim/         시뮬레이션 코어. Unity 패키지 형태 (package.json + asmdef)
  Runtime/     코드
  Tests~/      dotnet 프로젝트와 테스트. '~'로 끝나는 폴더는 Unity가 무시한다
game/        Unity 프로젝트. Packages/manifest.json에서 sim을 로컬 패키지로 잇는다
               "com.lostregalia.sim": "file:../../sim"
tools/       파이썬 도구 (문서 생성, 생성기, 계산)
balance/     경제 시뮬레이션
docs/        문서
```

- `sim/`은 Unity 프로젝트 바깥에 있다. Unity는 로컬 패키지로 읽고, `dotnet`은 같은 파일을 직접 컴파일한다. 코드는 한 벌이다.
- `data/`도 바깥에 있다. 에디터에서는 `../data`를 직접 읽고, 빌드할 때 에디터 스크립트가 `StreamingAssets`로 복사한다.
- 유료 에셋은 `game/Assets/ThirdParty/`에 두고 저장소에서 제외한다.

## 4. 이미 만든 것

설계가 성립하는지 확인하려고 시뮬레이션의 한 조각을 실제로 작성했다. Unity 6가 받아들이는 가장 보수적인 조합(C# 9, .NET Standard 2.1, 경고를 오류로)으로 컴파일한다.

| 파일 | 내용 |
|---|---|
| `Core/Rng.cs` | 난수. 상태가 값 하나 |
| `Core/MiniJson.cs` | 의존성 없는 JSON 읽기 |
| `Core/Hash.cs` | 상태 비교용 해시 |
| `Data/Defs.cs` | `king.json`과 `enemies.json`을 읽어 정의로 만든다 |
| `Rules/FallRules.cs` | 낙하 피해, 떨어뜨리는 데 필요한 횟수, 덮치기의 결과 |
| `Siege/Siege.cs` | 등반, 올라서기, 성벽 공격, 왕을 치기, 붙잡기와 회복, 추락, 연쇄, 다시 오르기 |
| `King/InputFrame.cs` | 틱 하나의 입력. 이동, 조준, 눌려 있는 버튼 |
| `King/King.cs` | 왕. 이동, 대시, 연타, 강공격, 받아치기, 맞기, 쓰러짐과 재기 |
| `World.cs` | 틱, 습격 시작(스폰 창과 레인 배정), 스냅숏과 되돌리기 |

### 4.1 테스트 결과

검사 116개가 모두 통과한다.

| 확인한 것 | 결과 |
|---|---|
| 데이터 읽기 | `data/`의 JSON을 그대로 읽는다. 적 15종 |
| **문서와 코드의 대조** | 낙하 피해(18m 146, 12m 65, 6m 16), 적 11종의 떨어뜨리는 횟수와 덮치기 결과가 [전투 규칙](./06_combat_rules.md)의 표와 같다 |
| 연쇄 추락 | 기본으로는 아래의 적이 버티고, '굴러떨어지는 것들'이 있으면 셋이 떨어져 위의 둘이 죽는다. 문서의 규칙대로다 |
| 결정성 | 같은 시드는 같은 상태 해시, 다른 시드는 다른 해시 |
| **되감기** | 20초 시점의 스냅숏으로 되돌린 뒤 다시 30초를 돌리면, 되돌리지 않고 돌린 것과 상태가 같다 |
| **왕** | 1초에 6m, 대시 7m와 재사용 2초, 연타 12 / 12 / 20과 이어지는 시간, 0.6초를 모은 강공격, 턱밑 띠와 등 뒤의 판정, 1.2초마다 맞기, 피격 후 무적, 받아치기와 반격파, 쓰러짐과 6초 뒤의 재기 |
| **입력만으로 막기** | 테스트용 왕이 상태를 읽고 입력(`InputFrame`)만 만들어 1장의 습격을 막는다. 시뮬레이션을 직접 건드리지 않는다 |
| 스냅숏 크기 | 적 12기일 때 396바이트 |
| 성능 | 적 200기일 때 틱 하나에 약 0.005ms. 틱 예산(33ms)의 6,000분의 1 |

### 4.2 돌려 보고 알게 된 것

- **첫 습격을 통째로 비우면 2분 안에 함락된다.** 등반병 10기가 성벽에 올라 초당 20씩 깎는다. 늦는 값이 "흑철 몇 개"가 아니라 "패배"가 되는 구간이 있다. 성벽 위 적의 피해를 낮출지, 그대로 둘지는 프로토타입에서 정한다. [전투 규칙](./06_combat_rules.md) 9장에 적어 두었다.
- **망설이지 않는 왕은 1장의 습격을 피해 없이 막는다.** 테스트용 왕은 실제로 걸어가고(초당 6m) 0.6초를 모아 친다. 그래도 언제나 가장 급한 레인으로 곧장 가므로 열두째 습격의 성벽 피해가 0이고, 왕도 한 대도 맞지 않는다. 1장의 어려움이 적의 수가 아니라 사람의 실수와 자리를 비우는 데서 나온다는 것이 수치로 확인된다.
- **강공격이 턱밑에서 모든 것을 끝낸다.** 테스트용 왕은 강공격 열한 번으로 열두 기를 모두 떨어뜨려 죽인다. 연타도 받아치기도 쓸 일이 없다. 등반병과 방패병만 오는 동안에는 "턱밑에서 모아 친다"가 유일한 답이 된다. 석궁수와 사다리가 들어와야 이 답이 흔들린다. 그래도 강공격이 지나치게 좋은지는 프로토타입의 확인 항목이다.
- **총공세의 석궁수는 칼로 못 잡는다.** 바위턱의 둘이 끝까지 남는다. 사격이 아직 코드에 없어 피해는 없지만, 검의 기본기만으로는 습격이 끝나지 않는다는 뜻이다. 검기(1단계 기술)나 발리스타가 있어야 한다. 의도한 그림이다.
- **절벽에서 죽은 적도 떨어진다.** 코드를 쓰다가 정한 규칙이다. 밀려서 떨어지든 맞아서 죽든, 절벽에 매달려 있던 적은 아래의 적을 덮친다.

### 4.3 아직 없는 것

고요·경보·습격의 주기와 함락, 왕의 귀환, 곶(타일, 채굴, 운반, 생성기), 경제, 각성 트리, 기술과 인장, 석궁수의 사격과 사다리, 방패병의 정면 방어, 성문길·공중의 적, 보스. 모두 같은 틀 안에 들어간다.

## 5. 시뮬레이션

### 5.1 틱

- 시뮬레이션은 초당 30번, 정해진 간격으로만 나아간다. `World.Step()` 한 번이 틱 하나다.
- Unity의 `Update`는 지난 시간을 모았다가 틱을 0~2번 돌린다. 화면은 직전 틱과 현재 틱 사이를 보간해 그린다. 60fps에서도 움직임이 매끄럽다.
- 입력은 프레임마다 모아 틱마다 한 묶음(`InputFrame`)으로 넘긴다. 이동 방향, 조준 방향, 누른 버튼. 시뮬레이션은 장치를 모른다.
- 메뉴가 열리면 틱을 돌리지 않는다. 그것이 일시정지다.

### 5.2 상태의 모양

```
World
 ├─ Tick, Rng                      틱 번호와 난수의 상태
 ├─ Phase                          고요 · 경보 · 습격 · 총공세 · 승리 · 함락, 남은 시간
 ├─ King            ← 전투만 작성됨  위치, 체력, 재사용 대기, 끌고 있는 자원, 비운 시간
 ├─ Siege           ← 작성됨        성벽 내구도, 적, 나타날 차례
 ├─ Facilities                     슬롯마다 종류·단계·특화, 재장전
 ├─ Cape                           다섯 땅의 타일, 캔 것, 자리, 물때
 ├─ Economy                        자원 넷, 부채
 ├─ Build                          깨운 노드, 장착한 기술, 인장, 룬, 진명, 성물
 └─ Story                          장, 대파편, 상처, 기억 조각
```

모든 상태는 `World` 아래에 있다. 전역 변수와 싱글턴에 게임 상태를 두지 않는다. 그래야 스냅숏 하나가 전부를 담는다.

### 5.3 적

- 적은 구조체다. 종류, 레인, 높이, 체력, 붙잡기, 상태, 타이머. 목록 하나에 줄지어 있다.
- 상태는 여섯이다. 오르는 중, 올라서는 중, 성벽 위, 바위턱, 떨어져 살아남음, 죽음.
- 길 찾기가 없다. 오르는 것은 높이에 속도를 더하는 일이다.
- 경로가 다른 적도 같은 방식으로 다룬다.

| 경로 | 위치를 나타내는 값 |
|---|---|
| 절벽면 | 레인 번호 + 높이 |
| 바위턱 | 레인 번호 + 높이(12m에서 멈춤) |
| 성문길 | 길 위의 거리 하나 |
| 공중 | 노리는 시설 + 남은 비행 시간 |
| 후방, 벼랑 턱 | 고정된 자리 |

### 5.3.1 왕

- 성벽 위의 자리는 좌표 둘이다. x는 성벽을 따라(0~40m), y는 벼랑 턱에서 성 안쪽으로(0~4m). 레인 여섯은 성벽 가운데 20m에 모여 있다.
- 근접 판정은 평면에서 잰다. 성벽 위의 적은 턱에서 1m 안쪽에, 턱밑 띠의 적은 그 레인의 턱 자리에 있는 것으로 본다. 띠 아래의 적은 근접에 닿지 않는다.
- **공격은 버튼을 뗄 때 나간다.** 누르고 있는 동안 모으고, 0.6초를 넘겨 떼면 강공격, 그 전에 떼면 연타 한 번이다. 동작 중에 눌렀다 뗀 한 번은 기억했다가 동작이 끝나면 낸다. 짧게 누를 때 한두 틱(0.03~0.07초)이 늦는 값이 손에 걸리는지는 프로토타입에서 본다.
- 성벽 위의 적은 왕이 4m 안에 있으면 성벽 대신 왕을 친다(1.2초마다). 왕이 쓰러졌거나 성벽에 없으면 성벽을 깎는다.
- 성벽 위의 적은 붙잡기가 깎이지 않는다. 한 번의 밀어냄이 붙잡기를 넘으면 벼랑 밖으로 떨어진다. 강공격(10)은 등반병(6)을 떨어뜨리고 방패병(12)은 못 떨어뜨린다.
- 틱 안의 순서는 왕이 먼저, 적이 다음이다. 같은 틱에 죽인 적은 치지 못한다.
- 쓰러지면 6초 뒤에 가득 찬 체력으로 성벽 가운데에서 일어난다. 왕좌와 안뜰이 좌표에 들어오면 일어나는 자리를 왕좌로 옮긴다.

### 5.4 기술의 조립

기술 하나는 코드가 아니라 데이터다. 쓸 때마다 아래 순서로 값을 만든다.

```
기술의 기본값 (data/trees/*.json)
   → 변형 분기 (A 또는 B)
   → 인장 (상태이상을 붙인다)
   → 룬 (소켓 1~3)
   → 깨운 수동 노드, 진명, 공명
   → 그 순간의 조건 (왕의 귀환, 연격의 누적 …)
   = 이번에 나가는 기술
```

- 전달 방식은 일곱이다. 호 베기, 직선 투사체, 낙하, 지대, 설치물, 소환수, 자기 중심 파동. 각각이 시뮬레이션의 시스템 하나다.
- 수식어는 "어느 값에, 더하기·곱하기·바꾸기 중 무엇을, 얼마나"로 적는다. 룬 '분열'은 "투사체 수 +1, 피해 ×0.6"이다.
- 더하는 것과 곱하는 것의 순서는 [전투 규칙 2.1](./06_combat_rules.md#21-피해)의 공식을 따른다.
- 태그는 장착한 것들에서 세어 공명을 켠다. 이것도 수식어의 묶음이다.

조합을 하나하나 코드로 쓰면 67만 가지를 감당할 수 없다. 전달 방식 일곱과 수식어 수십 개만 맞게 만들면 조합은 따라온다.

### 5.5 상태이상

적마다 인장 다섯 종의 칸이 고정으로 있다(남은 시간, 중첩). 상태이상이 걸릴 때마다 반응 표를 본다. 반응은 열 가지뿐이므로 표 하나로 끝난다.

### 5.6 곶

- 타일은 6바이트 안팎이다. 암반 종류, 남은 강도, 광맥의 종류와 양, 표시(갯골, 자리, 침식).
- 땅 하나가 864타일, 다섯 땅이 4,320타일. 전부 메모리에 있어도 30KB가 안 된다.
- 생성기는 `tools/cape_gen.py`를 C#으로 옮긴다. 규칙과 검증을 그대로 따른다([곶 생성 규칙 11장](./07_cape_generation.md#11-unity로-옮길-때)).
- **생성기는 정수만 쓴다.** 농성의 일일 시드는 모든 컴퓨터에서 같은 땅이 나와야 한다. 잡음과 보간을 정수로 계산해 컴퓨터마다 다를 여지를 없앤다.
- 왕은 곶에서도 시뮬레이션 안에서 움직인다. 타일 격자로 막힘을 판정하고 물리 엔진을 쓰지 않는다.

### 5.7 결정성을 지키는 규칙

| 규칙 | 이유 |
|---|---|
| `sim/`은 `UnityEngine`을 참조하지 않는다 | 어셈블리 정의가 컴파일 단계에서 막는다 |
| 시각과 프레임 시간을 읽지 않는다 | 틱 번호가 시간이다 |
| 난수는 `World.Rng` 하나 | 화면 쪽의 흔들림이나 효과는 별도의 난수를 쓴다 |
| 순서가 정해지지 않은 자료구조를 돌며 상태를 바꾸지 않는다 | 사전과 집합의 순회 순서는 보장되지 않는다. 목록을 쓴다 |
| 화면 쪽 코드는 상태를 읽기만 한다 | 상태를 바꾸는 길은 입력과 틱뿐이다 |

같은 컴퓨터에서 같은 결과면 충분하다. 되감기는 입력을 다시 돌리는 것이 아니라 스냅숏을 불러오는 것이어서, 실수 연산이 컴퓨터마다 미세하게 달라도 문제가 없다. 컴퓨터를 넘어 같아야 하는 것은 곶의 생성뿐이고, 그것은 정수로 푼다.

## 6. 저장과 되감기

| 항목 | 방식 |
|---|---|
| 형식 | 버전이 붙은 이진 스냅숏. `World.Snapshot()`이 상태 전체를 바이트로 뜬다 |
| 언제 | 고요가 시작될 때마다. 장이 시작될 때는 따로 보관한다 |
| 보관 | 최근 고요 3개 + 현재 장의 시작 + 직전 장의 시작 |
| 크기 | 스냅숏 하나에 수십 KB. 저장 파일 전체가 1MB를 넘지 않는다 |
| 파일 | 슬롯마다 파일 하나. 머리말(장, 플레이 시간, 형태)과 스냅숏들 |
| 쓰기 | 임시 파일에 쓰고 이름을 바꾼다. 쓰는 중에 꺼져도 직전 저장이 남는다 |
| 클라우드 | Steam 클라우드. 파일이 작아서 통째로 올린다 |

- **되감기**는 함락 화면에서 스냅숏을 골라 `World.Restore()`를 부르는 것이다. 따로 만들 것이 없다.
- **버전:** 스냅숏 머리에 버전 번호가 있다. 규칙 데이터가 바뀌어도 스냅숏은 읽힌다(스냅숏은 상태이고 규칙은 `data/`에 있다). 상태의 모양이 바뀌면 버전을 올리고, 옛 버전을 새 모양으로 옮기는 변환을 하나씩 추가한다.
- 농성의 한 판도 같은 방식으로 저장한다.
- 스냅숏은 디버깅 도구이기도 하다. 버그가 난 순간의 스냅숏 하나가 재현 방법이다.

## 7. Unity 쪽

### 7.1 프로젝트

| 항목 | 값 |
|---|---|
| 판 | Unity 6. 시작 시점의 최신 LTS |
| 렌더 | URP (가정) |
| 패키지 | Input System, Cinemachine. 나머지는 필요해질 때 더한다 |
| 장면 | 부팅 장면과 게임 장면 둘. 게임 상태는 장면이 아니라 `World`에 있다 |

### 7.2 시뮬레이션을 그리기

- 화면 쪽은 틱마다 상태를 읽어 보이는 것을 맞춘다. 적 하나에 뷰 하나가 붙고, 풀에서 꺼내고 돌려놓는다.
- 적의 화면 위치는 레인 번호와 높이에서 계산한다. 절벽 모델에 레인마다 곡선을 하나씩 심어 두고, 높이 값으로 그 위의 점을 찾는다. 절벽이 울퉁불퉁해도 시뮬레이션은 모른다.
- 소리와 효과는 시뮬레이션이 내는 **사건**으로 튼다. 떨어졌다, 죽었다, 성벽이 맞았다, 종이 울렸다. 화면 쪽이 상태를 비교해서 알아내지 않는다.

### 7.3 많은 적을 그리기

시뮬레이션은 200기에 0.01ms도 쓰지 않는다. 걸리는 것은 뼈대 애니메이션이 붙은 모델 200개를 그리는 일이다.

| 단계 | 방법 | 언제 |
|---|---|---|
| 1 | 그대로 그린다. 애니메이터와 스킨 메시. 화면 밖과 먼 것은 애니메이션을 줄인다 | 프로토타입, 버티컬 슬라이스 |
| 2 | 절벽을 오르는 적을 구운 애니메이션(정점 애니메이션 텍스처)으로 바꾸고 인스턴싱한다. 오르는 동작은 한 가지 반복이다 | 1단계로 목표 프레임이 안 나올 때만 |

2단계를 미리 만들지 않는다. 버티컬 슬라이스에서 적 150기를 놓고 재 본 뒤에 정한다.

### 7.4 타일 지형

- 타일을 8 × 8 묶음으로 나눠 묶음마다 메시 하나를 만든다. 타일이 파이면 그 묶음만 다시 만든다.
- 프로토타입에서는 타일마다 상자를 인스턴싱하는 것으로 충분하다(땅 하나 864타일).
- 지형에 충돌체를 두지 않는다. 막힘은 시뮬레이션의 격자가 판정한다.

### 7.5 물리

시뮬레이션은 PhysX를 쓰지 않는다. 성벽 위는 구간, 곶은 격자, 절벽은 레인이다. Unity의 물리는 부서진 돌 조각이나 떨어지는 시체 같은 **보이기만 하는 것**에만 쓴다. 떨어지는 적이 화면에서 어떻게 구르든 결과는 시뮬레이션이 이미 정했다.

### 7.6 입력과 카메라

- Input System으로 행동을 정의한다. 이동, 조준, 공격, 고유 동작, 기술 셋, 궁극, 대시, 상호작용, 내려놓기, 메뉴.
- 키보드·마우스와 게임패드를 처음부터 함께 지원한다. 게임패드의 조준 보조는 화면 쪽에서 조준 방향을 고쳐 `InputFrame`에 넣는다.
- 카메라는 Cinemachine 가상 카메라 둘이다. 성벽용은 벼랑 쪽으로 시점을 내리고, 곶용은 왕을 가운데에 둔다. 뒷문을 지날 때 섞어 넘긴다.

### 7.7 화면 UI

**UI Toolkit으로 만든다(확정).** UI는 에셋 팩을 쓰지 않고 직접 만든다. uGUI를 기본으로 두었던 이유가 에셋 팩이었으므로, 그 이유가 사라졌다. 게임 화면과 에디터 도구가 같은 틀을 쓴다.

| 항목 | 방법 |
|---|---|
| 구성 | 화면 하나에 문서(UXML) 하나. HUD, 왕좌 메뉴(탭 넷), 각성 트리, 성. `UIDocument` 하나에 올리고 화면을 바꿔 끼운다 |
| 모양 | 스타일 시트(USS) 하나에 색과 글자 크기를 변수로 둔다. [화면 설계서 3장](./09_screen_design.md#3-공통-규격)의 약속(금색 = 가진 것, 청록 = 미리 보기, 붉은색 = 위협)이 변수 이름이 된다 |
| 크기 | `PanelSettings`를 화면 크기에 맞춰 늘린다. 기준 1920 × 1080. 글자 크기 설정(100 / 115 / 130%)은 뿌리의 변수 하나로 바꾼다 |
| 값 잇기 | 화면은 틱마다 `World`를 읽어 바뀐 값만 요소에 쓴다. 요소가 상태를 바꾸는 길은 입력 명령뿐이다(5.7) |
| 직접 그리는 것 | 종 게이지의 고리, 재사용 덮개, 비운 시간 고리, 각성 트리의 고리와 선. 요소의 `generateVisualContent`에서 벡터로 그린다 |
| 각성 트리 | 별은 요소 69개, 선과 고리는 뒤에 깔린 요소 하나가 한꺼번에 그린다. 확대와 이동은 담는 요소의 변환으로 한다 |
| 전장 위의 표시 | 적의 막대, 윤곽선 옆의 표시, 피해 숫자, 왕의 고리. 세계 좌표를 패널 좌표로 바꿔 화면 위에 놓는다. 요소는 풀에서 꺼내 쓴다. 턱밑 띠의 윤곽선은 UI가 아니라 셰이더다 |
| 패드 조작 | UI Toolkit의 포커스 이동을 쓴다. 방사형 트리는 이웃을 직접 정해 준다(좌우는 같은 고리, 위아래는 안팎) |
| 글꼴 | 한글과 영문을 함께 담은 글꼴 에셋 하나. 글자는 쓰는 것만 굽는다 |

**확인할 것**

| 항목 | 내용 |
|---|---|
| 전장 위의 표시 200개 | 막대는 맞은 적에게만 붙으므로 실제로는 수십 개다. 그래도 많은 요소를 매 프레임 옮기는 값을 프로토타입에서 잰다. 무거우면 막대만 세계 쪽의 메시로 내린다 |
| 직접 그리는 요소의 갱신 | 고리는 값이 바뀔 때만 다시 그린다. 재사용 덮개처럼 매 프레임 바뀌는 것은 수를 센다 |
| 꾸밈 | 테두리 장식과 빛 번짐은 USS만으로는 한계가 있다. 화면 설계의 꾸밈 단계에서 필요한 만큼만 그림 조각을 만든다 |

- 에디터에서는 JSON이 바뀌면 다시 읽는다. 플레이 중에 숫자를 고치고 바로 본다.
- 밸런스 시뮬레이션(`balance/`)의 값도 같은 `data/`로 모은다. 지금은 스크립트 안에 있다. 옮기는 것이 남은 일이다.

### 8.2 식별자와 이름을 나눈다

지금 데이터에는 한글이 식별자로 쓰이는 곳이 있다(암반의 이름, 노드의 종류, 가지와 태그). 문서를 만들기에는 편하지만 코드와 번역에는 나쁘다.

| 지금 | 옮길 모양 |
|---|---|
| `"흙": 0.70` | `"dirt": 0.70` |
| `"kind": "진명"` | `"kind": "keystone"` |
| `"tags": ["추락"]` | `"tags": ["fall"]` |
| `"name": "검기"`, `"text": "…"` | `"id": "sword.flash.wave"` + 번역 표 |

- 식별자는 영문, 표시되는 글은 번역 표(`loc/ko.json`, `loc/en.json`)에 둔다.
- 문서 도구는 번역 표에서 한국어를 가져와 지금과 같은 문서를 만든다.
- 버티컬 슬라이스에 들어가기 전에 한 번에 옮긴다. 영어 번역 초안은 이 표에서 시작한다.

## 11. 만드는 순서

프로토타입 사양서의 주차별 작업을 이 구조에 맞추면 이렇다. 규칙은 `sim/`에 먼저 쓰고 테스트한 뒤 Unity에서 그린다.

| 순서 | 시뮬레이션 (`sim/`) | Unity (`game/`) |
|---|---|---|
| 1 | ~~왕: 이동, 대시, 체력, 쓰러짐~~ (작성됨) | 프로젝트 생성, 틱 돌리기, 왕의 뷰, 입력, 카메라 |
| 2 | ~~공격 판정(호, 원), 강공격, 받아치기~~ (작성됨) | 성벽과 절벽의 회색 상자, 적의 뷰, 레인 곡선 |
| 3 | 고요·경보·습격의 주기, 함락 | 종 게이지, 성벽 내구도, 종소리 |
| 4 | 곶: 타일, 채굴, 광맥, 운반, 생성기 | 타일 그리기, 해무, 빛의 실 |
| 5 | 경제, 노드 8개, 왕 강화, 시설 3종 | 왕좌 메뉴(목록), 성벽 띠 |
| 6 | 기술 3종, 석궁수의 사격, 대형 적 | 기술의 효과 |
| 7 | 스냅숏에 전부 넣기, 계측 기록 | 테스트 빌드 |

1번의 Unity 쪽 작업은 Unity가 깔린 컴퓨터에서 해야 한다. 시뮬레이션 쪽은 어디서든 쓸 수 있다.

## 12. 리스크와 미결

| 항목 | 내용 | 대응 |
|---|---|---|
| 보간의 손맛 | 30틱과 화면 보간 사이에서 입력이 한 박자 늦게 느껴질 수 있다 | 왕의 이동만 화면 쪽에서 먼저 움직이고 틱에서 맞춘다. 안 되면 틱을 60으로 올린다. 시뮬레이션 비용은 문제가 안 된다 |
| 뼈대 애니메이션 200개 | 그리기 병목 | 7.3의 2단계. 버티컬 슬라이스에서 재고 정한다 |
| 기술 조립의 표현력 | 전달 방식 일곱으로 안 되는 기술이 나온다 | 검의 기술 12개를 먼저 조립해 본다. 안 되는 것은 전달 방식을 늘리지 말고 기술을 고친다 |
| 한글 식별자 | 옮기기 전까지 코드에 한글 문자열 비교가 남는다(`"바위턱"`, `"소"`) | 8.2. 버티컬 슬라이스 전에 옮긴다 |
| 스냅숏 버전 | 얼리 액세스나 패치에서 저장이 깨진다 | 버전 변환을 테스트에 넣는다. 옛 스냅숏 표본을 저장소에 둔다 |
| 전장 위의 UI | UI Toolkit으로 적 머리 위의 표시를 많이 띄울 때의 비용을 모른다 | 7.7. 프로토타입에서 잰다. 무거우면 막대만 세계 쪽으로 내린다 |
| 렌더 파이프라인 | URP는 가정 | 에셋 팩을 고를 때 함께 정한다. 팩이 지원하는 쪽을 따른다 |
